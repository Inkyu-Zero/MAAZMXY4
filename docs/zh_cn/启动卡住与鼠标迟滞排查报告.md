# 启动卡住与鼠标迟滞排查报告

日期：2026年10月26日。范围：当前工程 `feat/script-studio` 的 Windows 前端、Python Agent、脚本回放和实时预览。

本报告先记录修复前的证据与方案，再记录实施结果。启动卡住已定位到 Agent 通信队列被实时预览事件填满；录制文件及宝烛流程可以正常执行。鼠标迟滞表现为真实指针速度骤降、移动不连贯，目前还不能确定唯一原因。

## 一、启动后一直转圈

**结论：已证实，是前端与 Agent 的连接问题。**

用户日志中的任务在17:04:18完成截图检查及脚本准备，17:04:19进入 `script_task_state`，随后没有返回。与此同时，MaaFramework反复记录 `server is not alive`，并未生成本轮初始化检查点。重启后的日志则完整记录了初始化、239个动作的48.4秒回放和返回确认，17:12:54正常完成。这排除了该录制文件无法加载这一解释。

故障链路如下：

1. MFA的 `AgentHelper.CreateAgentClient` 使用整个 `MaaTasker` 创建Agent客户端，连带订阅控制器、任务与上下文事件。
2. Windows实时预览不断产生截图事件。MaaFramework 5.12.3的控制器事件发送端只发送请求；Agent服务端仍返回响应。这些响应在空闲预览期间没有被持续取走。
3. 队列被填满后，Agent进程虽然仍在，通信通道却无法继续发送。该版本 `alive()` 实际检查通道是否可发送；“not alive”并不必然表示Python进程退出。
4. 原生通信默认等待上限极大，后续自定义动作可能长期等待。前端复用执行器时又只检查控制器是否连接，没有检查Agent通道，因此直接继续使用已堵塞的连接。
5. 重启清空了两端队列，所以暂时恢复；长时间停留在实时预览页后仍可能再次出现。

### 隔离复现

使用本机同版本原生库、独立Python Agent和只返回内存图片的控制器。测试不连接游戏、不发送键鼠输入。

| 仅绑定Resource中的自定义动作与识别回调 | 连续7000帧后仍存活，自定义动作成功；动作内部反向调用控制器截图也成功 |

生产日志位置为 `debug/maafw.bak.2026.10.26-17.04.18.752.log` 及用户导出的日志包。隔离复现结果保存在 `.runtime-cache/probe-preview-before.log` 和 `.runtime-cache/probe-preview-after.log`。

## 二、鼠标速度骤降和移动不连贯

**结论：尚未定位唯一根因，不能宣称已经修复。**

已核实的事实：

- 当前任务实际使用普通 `SendMessage`。运行日志中的 `with_cursor_pos=false`、`with_window_pos=false` 与配置一致；该模式的 `block_input` 默认也是false，因此这条输入路径不会主动调用锁输入或移动真实光标的分支。
- 当前48.4秒录制包含117次按下、117次抬起、两组鼠标按下/抬起和1次移动，不存在大量鼠标移动事件。
- 脚本工具的录制监听设置为 `suppress=False`；停止录制会停止、等待并核验监听线程退出。现有日志没有证明存在残留监听器，不能把它当作已确认原因。
- 一次4秒运行采样中，游戏约消耗1.23个CPU核心，MFA约1.14个CPU核心。这是按单核心折算的数据，不代表整机CPU占用超过100%，也不能单凭此数据证明鼠标迟滞由CPU引起。
- 已证实的Agent事件积压会增加无效通信和日志处理；它可能加重卡顿，但尚未建立与用户指针停顿时间一致的证据。

后续对照应保持相同任务和输入方式，分别观察实时预览开启/关闭时是否出现迟滞，记录发生时点，再对照进程负载和输入日志。当前前端已有“实时视图刷新率”设置，默认30帧/秒；可以在任务空闲时临时降至10帧/秒做对照，无需增加另一套限速实现。只有确认指针卡顿随预览负载变化，才能进一步认定这条因果关系。先消除已证实的事件积压，不贸然修改系统鼠标速度、强制抢占输入、切换输入模式或删除录制动作。

## 三、拟实施的修复

1. 使用Maa现有Resource绑定接口创建Agent客户端，保留自定义动作、识别及反向控制器调用，取消本工程不使用的高频事件转发。保持原有IPC/TCP选择。
2. 在复用空闲主执行器时检查Agent连接是否可用。失效时走工程已有的执行器和Agent重建流程；运行中的任务不因该检查被重建。此处只处理助手自己的Agent，不重启游戏。
3. 将真实原生通信的长预览回归测试纳入测试目录，覆盖预览之后执行动作、反向截图和连接失效检测，弥补此前仅在同进程中测试回放的缺口。
4. 构建新版前端，在任务停止且用户草稿安全的条件下安装。保持个人脚本、绑定和任务参数不变。

验收标准：长预览后任务不再卡在第一个自定义动作；正常任务仍能执行；失效连接能够被识别；鼠标迟滞只有在对照验证后才能标记为解决。

## 五、新截图中的实时预览提示

修复版启动时，17:38:37出现“实时画面已连接但无法获取画面（FramePool）”。随后现场检查确认：实时预览已正常显示游戏，刷新率约29帧/秒；原生截图初始化也已成功，测速约47毫秒。

这次提示来自 `TaskQueueViewModel.OnLiveViewTimerElapsed`：它异步提交截图后立即读取最近完成的缓存，第一次读取为空就发出警告，没有等待首帧的缓冲期。首帧到达后内部标志会复位，但先前的日志不会自动消失。因此该条历史提示不能用来判断当前截图仍失败；启动连接流程显示“任务已全部完成”也不表示副本脚本已经执行。

这是独立的提示时机问题，本次记录并解释，未通过更换截图模式或遮蔽真实失败提示处理。若后续实时画面持续为空，应重新排查窗口状态，而不能一概按首帧提示忽略。

## 七、2026-10-30：长时间挂机的输入延迟风险优化

用户反馈守卫太宗挂机几十分钟到数小时后，物理鼠标会每隔数秒跳动约半秒；当次未使用录制。拖动盒子时还曾出现普通桌面持续卡顿，但 Ctrl+Alt+Delete 界面仍流畅，返回桌面又卡。两程序同时退出后恢复，尚不能据此区分单个进程或确定拖动故障与周期性卡顿同因。

只读核验安装二进制、固定宿主源码和日志后，确认两项可避免的风险：

- `GlobalHotkeyService.InitializeAsPrimary` 只订阅键盘事件，却用 `SimpleGlobalHook()` 的默认 `GlobalHookType.All` 安装全局鼠标钩子。未进入录制也会运行此服务。Windows 低级鼠标钩子需要安装线程及时处理回调；托管暂停可能延迟物理输入。参见 [SharpHook 7.1.1 构造函数](https://github.com/TolikPylypchuk/SharpHook/blob/v7.1.1/SharpHook/SimpleGlobalHook.cs)和[微软鼠标钩子说明](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)。
- 宿主启动时创建 `AvaloniaMemoryCracker`，定期触发 GC，并在每次清理后调用 `SetProcessWorkingSetSize(-1, -1)`。该参数会尽量清空工作集，并非源注释所说的温和回收提示。重度策略还会多次进行阻塞式 GC；把调用放在后台线程不能隔离整个进程的托管暂停。参见[工作集 API](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsize)和[主动 GC](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/induced)。

本次按用户要求先做性能风险优化，由用户后续长时间使用观察效果：

1. 补丁 `55-keyboard-only-hotkeys.json` 明确使用 `GlobalHookType.Keyboard`，保留快捷键订阅、运行和退出逻辑。脚本录制器保持原行为。
2. 补丁 `56-runtime-managed-memory.json` 不再构造或启动周期清理器，交由 .NET 和 Windows 管理内存；保留原有可空退出路径，不创建闲置清理线程。不调整任务输入模式、实时预览帧率或用户脚本。

内存工作集可能不再定时下降，这是取消主动修剪的预期变化，并不等同于新增内存泄漏。游戏管理对盒子进程的内存阈值与重启策略不受影响。Agent 创建异常后的局部清理和应用退出资源释放不是周期路径，本次保留。

回归入口：`tests/test_frontend_input_latency.py`。设置 `FRONTEND_LATENCY_BUILD` 为前端输出或安装目录，`FRONTEND_LATENCY_DOTNET` 为 .NET 10 SDK 的 `dotnet.exe`。检查读取真实 `MFAAvalonia.Core.dll` 的 IL，不启动客户端、不安装钩子、不向游戏输入；旧安装应在鼠标钩子范围和周期清理器启动两项检查失败，新构建应通过。完整构建与安装哈希核对另行执行。

本轮验证：旧安装的两项二进制风险检查均失败，新构建通过；构建清单检查与补丁重复应用/损坏锚点拒绝检查通过。前端完成编译，并通过规范安装脚本更新本地客户端；安装文件与构建输出逐项核对，旧程序与用户数据均已备份。安装清单仅同步本次改变的前端 DLL 和构建记录摘要，资源版本保持不变。没有启动客户端或连接游戏测试。

本节记录的是风险优化，不能作为鼠标迟滞已根治的证明。真实长时间挂机与拖动故障未在本轮复现；依用户要求，由其后续使用反馈决定是否继续采样排查。
